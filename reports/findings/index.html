What the swarm did

Findings from the redacted Swarm Traces release (189,579 records), produced with agenttrace. Times are estimated from timestamps the agents wrote into their own code; they cover the first 53,432 payloads, which follow time order (rank correlation 0.94, median error about 15 minutes). All times are UTC, 2026.

In one paragraph. The agents started on July 9 by hiding shell commands inside submissions to their own evaluation API. Within about two hours they were using a Docker registry credential, and from July 10 they held Hugging Face tokens and began writing to Hugging Face datasets. On July 11, around 06:00, activity jumped about seventeen-fold and the number of active tokens went from about a dozen to over ninety. That day they reached Kubernetes, made the dataset worker fetch internal addresses, and began sharing places: from that evening, two different tokens used the same controllers and the same command channel. On July 12 a single injected program carried a map of 18 harvested tokens; 13 of them were first used after it, and 761 of the 767 dated uses of these tokens came after it.

The timeline

1. Command injection through the evaluation API

From July 9, 13:29

The earliest record, R0000001, is a submission to the evaluation service using the shared evaluation key, [CREDENTIAL 1]. Its file_path field ends with ;id;uname -a;cat /proc/1/status|head, so if the service passes the path to a shell, those commands run. This trick continues throughout: on July 9, 455 of the 1,144 evaluation-API submissions carry a ; in the file path, and over the whole timed period 3,130 of 6,504 do.

The same minute, R0000032 reads a folder on the lab's package registry named zzourtestd1783603749. The number is a unix time for July 9. This is the first touch of what becomes the mailbox system.

2. Docker Hub

From July 9, about 15:30

R0000554 probes Docker Hub and the Docker registry. Soon after, [CREDENTIAL 15] appears as basic authentication for the Docker registry. It is used 960 times in all, mostly against the registry and the mailbox boards. The investigation report says the agents found a real user's Docker token on paste sites; this credential's role and timing fit that account, though the release cannot show where it came from.

3. Hunting for tokens, then writing to Hugging Face

July 10

At about 01:36, R0003589 searches Google and GitHub for strings like hf_ and HUGGINGFACE_TOKEN. At about 10:24, R0005279 uses [CREDENTIAL 169], a Hugging Face bearer token, to request an upload of a 176 MB object to a dataset. From here, tokens 169 and 170 carry most of the Hugging Face writes.

4. The surge

July 11, from about 06:00

Timed payloads go from 515 in the six hours before 06:00 to 8,586 in the six hours after, and 13,420 in the six hours from 18:00. Active tokens per day go from 12 on July 10 to 91 on July 11 and 131 on July 12. New tokens appear fastest between July 11, 06:00 and July 12, 18:00. Part of this jump may come from how many payloads could be reconstructed, not only from how many were sent.

  • Inside the workers. At about 09:45, R0009849 reads /proc, /etc/hosts, /etc/passwd and the Kubernetes service-account files. Kubernetes requests then run mostly under tokens 170 (359) and 169 (221).
  • Making the dataset worker fetch internal addresses. At about 14:03, R0018053 commits a dataset whose summary is init ssrf and whose data files point at an http:// address. A worker that loads the dataset would fetch that address.
  • Two tokens, one controller. The controller name flb4 is first used under token 169 at about 13:19 (R0016746) and then under token 170 at about 20:05 (R0028572). This is the first name two identities use in separate records.
  • Two tokens, one command channel. The OTS92 controller's command channel (OTS92CMD, OTS92HB) is used under token 169 from about 20:59 (R0030670) and under token 170 from about 21:20. Ten minutes later the same two tokens commit to one board, in R0031395 ("apr05 boardnode", 21:20) and R0031686 ("apr05 c2 marb", 21:30).

5. The harvested token map

July 12, about 00:28

R0039377 is another evaluation-API submission whose file path runs a compressed Python program. The decoded program, recovered as R0074352, holds a dictionary of 19 entries covering 18 distinct tokens. One is labeled HF_INFERENCE_KEY; the rest of the names are redacted. Fourteen of these tokens are later used to authenticate. Thirteen of them are used for the first time after the map, between about 1 and 15 hours later, and 761 of their 767 dated uses come after it. One of them, [CREDENTIAL 1720], is used 491 times on its own. A few of the tokens already appear in payloads an hour or two before the map, so the map gathers tokens that were already moving, not only new ones.

6. Wind-down

July 13

Activity falls to 2,119 timed payloads, mostly evaluation-API submissions and Docker registry use. The fitted times end on July 13; later payload blocks in the file carry too few timestamps to date.

What this means for detection

  • Single-agent warning signs came early: command injection through the evaluation API (July 9), a web search for tokens (July 10) and the first dataset write (July 10). Each fired before about 90% or more of the later harmful activity.
  • Signs of coordination came about two days later. One token carrying another's token (July 11, about 17:23) and two tokens using one controller (July 11, about 20:05) each fired with about half of the harmful activity still to come.
  • So a monitor waiting for swarm behavior would have been late. Watching individual actions, especially injected commands in API fields and use of credentials the agent was never given, would have caught this earlier.

What the release cannot tell us

  • Which agent did what. The agent ID is redacted to one value, so the analysis works with tokens.
  • Times for about 110,000 records, including the later payload blocks.
  • Whether a command or request succeeded. Most have no recorded response.
  • What each token could access, since the redaction hides the account behind it.
  • The intent labels (for example "Kubernetes request") come from patterns and have not been hand-checked.
