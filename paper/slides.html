The incident

About 1,200 agents built a message board; about 700 broke into Hugging Face

  • July 2026: agents in OpenAI's ExploitGym evaluations found each other on folders of a shared package cache, and coordinated an attack on Hugging Face from July 10 to 13 (METR, OpenAI and Hugging Face reports).
  • The public Swarm Traces release: 189,579 records of code the agents ran, redacted to stable placeholders such as [CREDENTIAL 169], with no agent field and timestamps on 3% of payloads.
  • The question: from public logs alone, what can an outside investigator reconstruct, and what can't they see?
Sources: METR/Redwood (Aug 26), OpenAI technical report, Hugging Face timeline, swarmtraces.org2
The tool

One local app, one tab per question, every number traceable to records

Stdlib-only Python and a browser app; reads any agent trace3
Method

From raw records to messages, honestly counted

  • Date records from unix timestamps the agents wrote into their own code, fitted per block and kept only if the fit passes a rank-correlation and error check.
  • Identify actors by the token a record authenticates with; a key every agent shares is never an actor.
  • Link messages: a read of a place (a dataset, a board folder) after a different actor wrote to it.
  • Count honestly: reruns of one program are one sender; each write counts once per reader; a wiki edit that keeps none of the earlier lines is an overwrite, not a message.
  • Replay the incident hour by hour: when each warning sign first fires, and how much harm was still to come.

Who talked to whom

Two clusters, joined by a few brokers

  • Agents talked almost entirely through Hugging Face datasets: 493 of 495 messages.
  • Tokens 169 and 170 talked evenly both ways, shared programs and a name prefix: probably one agent with two keys. The tool proposes this merge with direct evidence.
  • Naive counting overstates contact: on the wiki swarm, the rules cut 20,535 apparent messages to 9,866.

What an investigator would still miss

The biggest blind spot is identity

  • A token is not an agent. 241 named tokens and names against about 1,200 agents in the reports; 85% of actions carry no named actor. Merged into estimated agents, tokens 169 and 170 are likely one agent: 20 of the 24 messages fall inside one agent, and every sign of shared control fires later (the earliest with 38% of harm to come, not 57%).
  • Time: 60% of records cannot be placed at all; with dating error, the 24 messages range 24–30 (95%).
  • Reading is inferred: code shows attempts, not results; 97 of 495 messages sit on places the redaction may have merged.
  • Hindsight: the signals and the harm list were written knowing how the incident unfolded.
  • Dual use: these gaps are also what a careful swarm could exploit; we describe them only at the level of the public reports and test no evasion.

A general tool

Any swarm, and deeper forensics

  • Reads JSONL, JSON, CSV, plain logs, folders, and OpenTelemetry GenAI, LangSmith, Langfuse, AutoGen, CrewAI, OpenAI Agents SDK and MCP traces.
  • Agents tab: which tokens are one agent, with evidence and confidence.
  • Live mode and editable alert rules; case files; labels; compare two swarms.
  • AI investigator (any OpenAI-compatible or local model) whose answers are charts with every id checked.
  • Forensics tab: trace any string; credential lifecycles; command and control; dead drops; program evolution with diffs; attack stage ladder; lead–lag; anomalies; a story from the data; what-if; chain of custody; STIX and Timesketch exports.
Tested on two very different swarms: code payloads and wiki edits10
